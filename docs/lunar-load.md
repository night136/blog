# 农历库加载：为什么「连续刷新」挂件一直是空的

> 2026-09-15 诊断 + 修复。相关：`docs/mobile-review.md`（窄屏按需加载的由来）、`docs/domestic-acceleration.md`（跨境链路）。
> 回归：`scripts/verify-lunar-boot.mjs`（40 项，含假定时器把 onerror / 挂起 / 超时三种路径真跑一遍 + 4 项负向验证）。

## 一、症状

桌面端右侧栏「🌙 农历」挂件只剩一个空心圆和四个「—」，hero 那行「🕐 申时 15:36:58」
一切正常 —— 连刷几次都是这样，控制台没有任何报错。

## 二、三个原因叠在一起

### ① 挂件在库落地前就是这个样子（设计如此，但没有任何解释）

`lunar.js` 426KB（br 约 110KB），是**空闲时懒加载**的：

```js
if (!isNarrow()) window.requestIdleCallback(loadLunarLib, { timeout: 2000 });
```

在它下载完成之前，`#lunarGanZhi` 等 5 个字段就是 HTML 里写死的占位 `—`。
跨境链路（本机实测到 CF 边缘约 1s / 请求）下，从导航到挂件出现要 2~3s。
**这期间页面看起来就是「坏了」，而不是「在加载」。**

### ② 失败是静默终态（真正的 bug）

原实现只有一行：

```js
s.onerror = function () { lunarLibState = "failed"; heroLineKey = ""; try { tickClock(); } catch (e) {} };
```

而失败文案只在 `isNarrow()` 时才渲染 → **宽屏用户什么都看不到**。
更糟的是失败后既不重试也没有入口（点击重试的提示只在窄屏出现），
于是一次偶发失败（跨境下载被掐断）就让农历**永久**失灵。

沙箱复现（`node scripts/verify-lunar-boot.mjs` 的第 [5] 节，修复前）：

```
❌ 失败后立即给出可点重试的提示（宽屏原先什么都不显示）
   实际: 🕐 <strong>申时</strong> <span class="lunar-time">15:41:02</span>
❌ 第 1 次退避后自动重试
   实际: 实际请求次数=1
```

还有一条更隐蔽的：**请求挂着不返回**（连接建立后没响应）时 `onload`/`onerror` 都不触发，
状态永远停在 `loading` —— 也是静默的、也不可恢复。

### ③ 刷新会把没下完的下载掐掉

文档卸载时在途请求被中止，而 `max-age=86400` 的**浏览器缓存只有下载完成后才写入**。
所以刷得比 110KB 下载快，就每次都从头开始、永远下不完 —— 这正是「连续刷新一直空」。
一旦成功下过一次，24h 内都是秒开（这也是为什么它不是每次都能复现）。

## 三、修法

| # | 改动 | 文件 |
|---|---|---|
| 1 | `onerror` / **看门狗超时**都走同一个 `lunarFail()`；退避自动重试最多 3 次（1.5s / 5s） | `assets/app.js` |
| 2 | 失败/重试中时，**宽屏** hero 行也给出「农历加载失败 · 点按重试」并标记可点（正常态零变化） | `assets/app.js` |
| 3 | 侧栏挂件主行不再空挂「—」：未就绪显示「农历加载中…」，失败显示可点重试，失败态整块可点 | `assets/app.js` + `assets/style.css` |
| 4 | `onload` 后仍无 `Lunar` 全局也算失败（响应被代理/过滤插件替换过时 onload 照样触发） | `assets/app.js` |
| 5 | `<link rel="preload" as="script" media="(min-width: 981px)">`，把下载提前到解析阶段，与 app.js/style.css 并行 | `index.html` |

**人工重试会重开预算**（`lunarAttempts = 0`）：自动重试用尽后点一下仍能救回来，
否则用户只剩硬刷新一条路。

### 为什么看门狗不是「多此一举」

跨境链路上「连上了但不返回」比「明确 404」常见得多，而它对前端就是彻底静默。
15s 后按失败处理，比永远停在 loading 强。

### 为什么预加载要带 `media`

窄屏（≤980px）右侧栏整体 `display:none`，农历挂件根本看不到 ——
`0b67f20` 特意让窄屏不下载这 110KB（见 `docs/mobile-review.md`）。
预加载必须用同一个断点门控，否则会把省下来的流量又加回去。
**`media` 属性在 preload 上是规范行为（不匹配则不发起请求），不是装饰。**

⚠️ **两处 URL 必须完全一致**（都不带 `?v=`）：`index.html` 的 `href` 与 `app.js` 的 `LUNAR_SRC`。
不一致的话预加载拿到的响应不会被注入的 `<script>` 复用 → 白下 110KB 还要再下一次。
回归脚本第 [10] 节专门钉这两条。

## 四、怎么自己复核

1. **正常加载**：桌面端打开，挂件先显示「农历加载中…」→ 一两秒内变成干支 + 月历。
2. **模拟失败**：DevTools → Network → 右键 `lunar.js` → **Block request URL**，硬刷新。
   预期：hero 行出现「农历加载失败 · 点按重试」，挂件显示失败文案；
   Network 里能看到 1.5s、5s 两次自动重试（共 3 次请求）；点一下挂件/hero 行能立刻再试。
3. **模拟挂起**：Network 面板的 `Slow 3G` + 关掉缓存硬刷新，看 15s 后是否转为失败（而不是一直 loading）。
4. **预加载是否复用**：Network 面板应只有**一条** `lunar.js` 记录（`Size` 是缓存/预加载，
   不该出现两条 110KB 的下载）。
