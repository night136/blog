# 头像素材：为什么必须是「正方形 + 图案居中 + 不透明」

> 2026-09-16。起因：用户反馈「头像周围的空区域没对齐好」（注意——**不是位置问题**，是图案四周那圈
> 留白不匀）。相关守护：`scripts/verify-avatar-asset.mjs`（13 项，含正负向自证）。
> 生成脚本：`scripts/build-avatar-asset.py`。测量脚本（均在 gitignore 的 `.diag/`）：
> `avatar-probe.mjs`、`measure-ring-tol.py`、`compare-model-vs-shot.py`、`ascii-avatar.py`。

## 病灶：三处叠加，读 CSS 永远查不出来

`.hero-avatar` 的 CSS 完全正确（`width/height:72px; border-radius:50%; object-fit:cover; margin:0 0 14px`）。
错的是**位图内容**：

1. 旧 `assets/logo-*.png` 是 **183×130 非正方形**，图案圆盘（94px）在其中偏左上；
2. CSS 是 `object-fit: cover` —— cover 按**大的那一边**缩放，另一边超出部分居中裁掉。
   宽高比 ≠ 1 时**只裁一个方向**（这里是左右各裁 26.5px、上下不裁），
   源图里图案的偏移就被**原样**带进了圆盒；
3. 旧素材是 **RGBA（透明底 + 软边）**，整图 **14.4% 像素透明**。

## ⚠️ 最值钱的教训：透明度会让测量变成**虚构**

第一版守护脚本的解码器只展开 RGB、**把 alpha 丢掉**，于是量出
「图案 94px、底圈 上6.1/下13.8」，还据此宣称「观感与改造前一致」。
**这组数字一半是透明像素的原始 RGB —— 现实中不存在。**

透明像素的 RGB 不是屏幕上能看到的颜色。软边合成到奶油色卡片上之后**整片消失**，
所以浏览器实际只画 **39×39px**。

**规则：量任何位图之前，先按 alpha 合成。**
自己写零依赖解码器时：读 colorType 4/6 的 alpha 通道，**遇到 `tRNS` 直接报错**
（宁可拒绝，不可静默忽略 —— 静默忽略就是上面这个事故）。

## 真实口径与数字

判据：与**圆外卡片底色**逐通道差 > 18 的像素算「图案」；真实浏览器 2× 设备像素截图；
TOL 取 18/30/45 **三档同值**才算稳定。显示尺寸 72×72px。

| | 图案 | 中心偏移 | 底圈 上 / 下 / 左 / 右 | 上下差 | 左右差 |
|---|---|---|---|---|---|
| 修复前（旧素材） | 39.0×39.0px | **(+2.0, −4.0)** | 12.5 / 20.5 / 18.5 / 14.5 | **8.0px** | **4.0px** |
| 修复后（新素材） | 51.0×52.0px | **(0.0, 0.0)** | 10.0 / 10.0 / 10.5 / 10.5 | **0.0px** | **0.0px** |

**交叉验证**（这是唯一能排除「测量工具在撒谎」的手法）：把旧素材按 alpha 合成到卡片底色、
再按 CSS 语义（cover → resize → 圆形裁剪）推算 → **38.8×38.8px / 12.7·20.5·18.6·14.7**，
与浏览器实测差 **0.2px** ⇒ 机制确认。

注意：**中心偏移两组口径一致（±0.5px 内）**，所以「没对齐」这个结论从一开始就没变；
变的是「图案多大 / 底圈多宽」。

## 修复流程

1. **母版入库**：`assets/src/logo-original.jpg`（1133×1080）。用户是从微信发的，
   微信临时文件会消失 —— 丢了就没法重建。
2. **拟合图案圆心**：720 个角度向外扫第一处暗像素当外沿 → 最小二乘拟合（Kåsa 代数拟合 +
   手写 3×3 高斯消元，**不依赖 numpy**）→ 迭代 4 轮剔除离群点（残差 > 4×中位数），
   箭头造型会贡献 6 个离群点。
   结果：圆心 **(561.48, 553.08)、半径 447.09**；而图心是 (566.5, 540.0)
   —— **图案本身就偏 (−5.0, +13.1)**，这就是当年「按图心裁切」错位的根因。
3. **强制正方形裁切**：四边用同一个 `crop_side = round((r + margin) * 2)`。
   ⚠️ 逐轴写 `round(cx ± r)` 会产出 899×898 —— 0.11% 的椭圆，72px 下表现为 0.25px 左右不对称。
4. **正方形画布 + 居中**：288×288、256 色调色板（24KB，是旧 18KB 的 4 倍线性分辨率），
   4× 超采样圆形蒙版。旧素材那条黑边是「白色被填成黑」的意外产物，**没有复刻**。
5. **必须不透明**：透明处的颜色由页面底色决定 ⇒ 暗色模式下底圈会变成深色，
   深墨图案和它糊在一起。脚本保存前硬拒带透明度的输出。

```bash
python scripts/build-avatar-asset.py --check              # 只报几何，不写盘
python scripts/build-avatar-asset.py                      # 重建两个 logo
python scripts/build-avatar-asset.py --disc-ratio 0.54    # 图案更小 / 底圈更宽
node scripts/verify-avatar-asset.mjs
```

## 换图后必须能刷掉缓存

`/assets/*` 是 `max-age=86400 + stale-while-revalidate=604800`。同名换图不换 URL 会被缓存
最多一天，用户会以为「改了没生效」。所以 `build.mjs` 的 `hashAssets()` 里**逐个登记**了
`logo-avatar.png` / `logo-hero.png`，构建时注入 `?v=<内容哈希>`（稳定文件名，不玩哈希文件名 ——
陈旧外壳会引用到已删除的文件 → 404）。

部署判据：线上 `/assets/logo-avatar.png?v=<hash>` 的**字节 sha256 与本地完全一致**。
⚠️ 不能只看 `app.js` 的 `?v=` —— 换图时它不变，拿它当判据会一直「没部署」。

## 图案该多大（设计选择，不是不变量）

旧素材**实心内容**的比例是 72%（94/130），守护按这个比例重建；但旧素材那圈软边在浏览器里
被合成成了卡片底色、等于不可见，所以旧版**肉眼**看到的图案只有 39px（54%），新版是 51px（72%）
—— **图案看着变大了**。想保持旧观感就 `--disc-ratio 0.54`。

守护只断言**区间**（0.5 < 占盒 < 0.98），**不钉死数值** —— 这是审美，不是 bug。

## 两条测量纪律

- ⚠️ **别用亮度阈值找圆形图案的边缘。** 太极/水印类图案有**与底色同色的浅部**，阈值扫描会把
  浅部当背景，量出非方形的假包围盒（本轮扫出 49×81 的「图案」）。改用「与圆外底色逐通道差 > TOL」。
- ⚠️ **截图像素 = CSS px × dpr。** `getBoundingClientRect()` 给 CSS px，
  `Page.captureScreenshot` 出设备像素（本轮 1265×2 = 2530 宽）。拿 CSS 坐标直接裁图会裁错位置，
  读出一片纯色 —— 极易误判成「图案没渲染」的假故障。**先确认截图宽 = 视口宽 × dpr 再裁。**
