## 三、🔴 P0 — 首绘被阻塞的外部样式表卡住（最大单项收益）

### 证据链（三步，互相独立）

1. **增量对比**：首页从 HTML 到首绘要 **658ms**；同一个站、同一台机器、同一时段，`/404.html` 只要 **55ms**。两者唯一的差别就是后者**没有外部样式表**（774 字节的 HTML，CSS 全内联）。
2. **资源时序**：`/assets/style.css` 实测传输 32868 B（br）、总耗时 **534 ms**，FCP 1420ms 紧跟在 style.css 完成后。
3. **排除法**：长任务 0 个、控制台 0 错误、DOM 节点仅 583 —— 首绘延迟不是 JS 或 DOM 造成的。

⇒ **从 HTML 到首绘的 658ms 里有约 600ms 是在等一张 108KB（br 32.9KB）的阻塞样式表。**

### 为什么这件事值得做

- 首绘是用户对「站点快不快」的**唯一主观判据**。658ms → 约 100ms 是**6 倍**量级的改善。
- 这是**唯一一个**能一次性改善所有页面（首页/文章/留言墙）的优化。
- 现在的 index.html 已经内联了「变量 + 防闪 + 布局骨架 + 卡片入场动画 + 移动端兜底」，**证明内联这条路在本项目可行** —— 只是范围还不够。

### 修法（两条路，风险不同，必须二选一并实测）

| 方案 | 做法 | 收益 | 风险 |
|---|---|---|---|
| **A 保守** | 扩大内联范围：把首屏可见区域的规则（topbar / hero / 布局栅格 / 卡片 / 侧栏）也内联进 `<head>` | 中（可能 200~400ms） | 低。HTML 体积增大约 6~8KB（br 后） |
| **B 激进** | 拆成 `critical.css`（内联）+ `rest.css`（首绘后由 app.js 注入，**复用现成的字体注入手法**） | 高（接近 658ms 全拿） | 中。注入晚了会 **FOUC**（首绘后样式跳变），必须实测 |

### 🚫 三个已知雷区（本项目都踩过）

- **不能用 `media="print" onload` 切换**：小米/360 兼容模式支持不良，会导致样式表**永远不生效**，项目已因此回滚过一次（见 `docs/first-paint.md`、`index.html` 第 184 行注释）。
- **不能把字体注入的注释当成 style.css 的方案**：那两段注释现在是混在一起的（见 §十）。
- **注入式方案必须造一次真实调用证伪「不会 FOUC」**：不能只看代码写完了。历史上「假兜底」已经骗过我们一次（`89838d8`，注释写着「等事件自动触发」而那个事件会抛异常）。

### 前置验证要求（做之前先建判据）

- 在**真实浏览器**里同时量 FCP 与 **CLS**（样式跳变会体现为 CLS）。
- 冷缓存 + 暖缓存各跑一次（暖缓存下网络代价消失，若仍有跳变说明是注入时机问题，不是网络问题）。
- 移动视口单独跑（窄屏分支的规则更多）。

## 四、🟠 P1 — 首屏白下 24.8KB：两个 logo 是同一张图

### 证据

```
本地 md5：assets/logo-avatar.png = bead8fd2d4ff3b5c10f63f532286da47
          assets/logo-hero.png   = bead8fd2d4ff3b5c10f63f532286da47   ← 完全相同
线上 etag：/assets/logo-avatar.png?v=c9278a5d61 → "dd8296b56334dd36216deaf61312f81e"
          /assets/logo-hero.png?v=c9278a5d61   → "dd8296b56334dd36216deaf61312f81e"  ← 同一个 etag
```

冷缓存实测（真实浏览器）：两个请求**同时**在 +772ms 发起，各自传输 **24830 B**（耗时 273ms / 300ms）。
`index.html` 里确实用了**两个不同的 URL**：

```html
209: <img class="avatar"      src="assets/logo-avatar.png" ... width="56" height="56">
250: <img class="hero-avatar" src="assets/logo-hero.png"   ... width="72" height="72">
```

⇒ 浏览器按 URL 做缓存键，**同一张图被下载了两次**。

### ✅ 已修（提交 `2733ab4`）

用 `.diag/count-logo-requests.mjs`（真浏览器 + 全新 profile + `Network.clearBrowserCache`）前后各量一次：

| | logo 请求数 | 传输字节 |
|---|---|---|
| 改前（线上） | 2（两个 URL 各 1 次） | **49665 B** |
| 改后 | **1** | **24724 B** |

⇒ 首屏省 **24941 B（≈24.4 KB）**、少一次往返，渲染零变化。

**实际做法与原计划有一处不同：没有删文件。** 原计划写「只留一份、删掉另一个」，但任何
**陈旧 HTML 外壳**（Cloudflare 边缘 `swr` 副本、用户已缓存的 HTML）仍引用着
`assets/logo-hero.png`，删了就 404 破图 —— 这正是 `build.mjs` 注释里记录过的 2026-09-12
事故类型（哈希文件名随部署消失 ⇒ 陈旧外壳 4/4 次 404）。

收益来自「**只有一个被引用的 URL**」，与文件是否删除无关。所以 `logo-hero.png` 保留为
**兜底副本**（不再被引用）。配套：

- `index.html` 两处头像统一用 `assets/logo-avatar.png`（渲染尺寸由 `width/height` 决定，与下载份数无关）；
- `build.mjs` 注入正则写成 `logo-(?:avatar|hero)`，把历史引用顺手收敛回唯一 URL（构建期防复发）；
- `verify-avatar-asset` 新增 4 条不变量：`index.html` 里 logo 引用**去重后必须只有 1 个 URL**、
  两侧头像指向同一 URL、兜底副本与主素材**字节必须相同**（漂移会「只在缓存命中时画出旧头像」，
  这种差异最难查）、`build.mjs` 必须保留归一化与 `?v=` 注入；
  同时把 `logo-hero.png` 改成「允许不存在」，将来清掉兜底副本不该判红。

⚠️ 将来真要删兜底副本，先确认线上已无 `logo-hero.png` 引用、且过了至少一个 `swr` 周期。

## 五、🟠 P1 — 登录是全站唯一没有防护的入口

### 现状（代码核实）

| 入口 | Turnstile 人机验证 | 失败次数限制 |
|---|---|---|
| `POST /api/register` | ✅ 有（`verifyTurnstile`） | — |
| `POST /api/guestbook` | ✅ 有 | ✅ 有（`DAILY_LIMIT = 5`） |
| **`POST /api/login`** | ❌ **无** | ❌ **无** |

`login.js` 里只有防**用户名枚举**的措施（两分支文案一致 + 假哈希 + 时序防护），但**没有任何东西阻止反复尝试**。

⇒ 也就是说：注册口有人机验证挡着，**登录口没人管**。攻击者不需要注册，直接对着登录口无限试密码即可。

### 修法（三件，可分开做）

1. **给 login 挂 Turnstile**：与 register 共用一个 Site Key（前端已有 `renderTurnstile` / `renderRegisterTurnstile` 两套渲染，加第三套或复用即可）。
2. **基于 IP + 用户名的失败计数**：计数存 D1（新表 `login_attempts`），超过阈值后**递增延迟**而不是硬锁（硬锁会被用来 DoS 真实用户）。
   ⚠️ `getClientIp()` 已在 `functions/api/_lib/turnstile.js` 里，直接复用。
3. **PBKDF2 渐进升级**：现在 `iterations: 100000`（`auth.js:28`），OWASP 当前建议 600000。
   🚫 **绝不能直接把 100000 改成 600000** —— 所有现存密码会立刻全部校验失败。
   正确做法：把迭代数**写进 hash 字符串**（`pbkdf2$<iter>$<salt>$<hash>`），校验时按**存储的**迭代数算；老格式 `salt:hash` 按 100000 校验，**成功后顺手用新迭代数重写**。这样不用重置任何人的密码。

## 六、🟠 P1 — 首页就加载 Turnstile，而首屏完全用不到

### 实测

冷缓存首页上，Turnstile 相关请求：

```
/turnstile/v0/api.js?render=explicit   开始 +1604ms   耗时 866ms
/cdn-cgi/challenge-platform/...        开始 +2485ms   耗时 836ms
/cdn-cgi/challenge-platform/...        开始 +2483ms   耗时 826ms
challenges.cloudflare.com iframe       2 个           合计 1662ms
```

### 为什么是浪费

人机验证只有两个用途：**注册**、**留言墙**。首页列表、文章详情、归档、关于页**都不需要**。

### ⚠️ 把 #11 修错了一次（2026-09-17，值得单独记）

第一版按上面那句「加上 `max-age` 即可」做的：给三个端点加了

唯一差别是没用 Cache API）实测：

| 端点 | Cache API | `s-maxage` | 实测 |
|---|---|---|---|
| `/api/posts/meta` | ✅ | ✅ | `cf-cache-status: HIT`（age 15→25→33 递增） |
| `/api/_probe-a/b/c/d` | ❌ | ✅ | **连 `cf-cache-status` 都不出现** |

⇒ 根因**不是** Content-Type、也**不是** SWR（这两组变量都单独隔离过），而是
**Pages Functions 的响应不会因 `s-maxage` 自动进 CDN 缓存，必须用 Cache API 显式写**。
仓库里其实早写着这句 —— `functions/api/posts.js:58`：

> `// 边缘缓存：Pages Functions 不会因 s-maxage 标头自动走 CDN 缓存，必须用 Cache API 显式存边缘。`

**教训**：判据必须是**目标本身**，不能是它的代理指标。
「响应里有 `Cache-Control`」是代理指标，「命中缓存时不打 D1」才是目标 ——
后者能一眼看穿这个错。现在守护里的判据就是后者：
把 D1 换成**必炸**的实现，只要缓存还能正常返回，就证明它压根没走到 D1。
（这与 `verify-first-paint` 当初写死「注入点在 /api/config 之后」是同一类错误：
**盯不变量，别盯代理指标**。）

### 实测（`audit-live.mjs`）

|---|---|---|

**根因**：`_headers` 只对**静态文件**生效，Functions 返回的响应不经过它。所以 `/api/*` 与三个 XML/TXT 端点连基础的 `nosniff` 都没有。

### 修法（实际落地）

- `functions/_lib/security.js` —— 6 个头的**唯一来源**。
- `functions/_middleware.js` —— 放在 `functions/` 根，给**所有**函数响应兜一层。
  ⚠️ 用 `onRequest` 而非 `onRequestGet`（写接口全是 POST/DELETE，否则漏掉一半）。
  ⚠️ 这一层**只加不删**：只 `set()` 那 6 个头，绝不碰 `cache-control` / `content-type` / `set-cookie`。
  （静态资源的缓存策略来自 `_headers`，被这一层改写就是全站缓存策略崩掉；`set-cookie` 一丢，登录就静默失效。）
- `_headers` 全局块同步补上 HSTS / XFO / Permissions-Policy / CSP。

**CSP 只上了不需要 nonce 的那一半**：`object-src 'none'; base-uri 'self'; frame-ancestors 'none'`
（依据：全仓 0 个 `<object>` / `<base>` / `<iframe>`，真 grep 过）。
`script-src` / `style-src` **仍然没上** —— 页面有 3 段内联 `<script>`，
`build.mjs` 还会把整张 `style.css` 内联进 `<head>`，直接上会当场白屏；要上得先给它们算 hash/nonce，
**另立一项**。

### 两个值得单独记的取舍

1. **HSTS 不带 `includeSubDomains`**：`pages.dev` 是所有 Cloudflare Pages 项目共用的域，
   加了等于替别人的项目做主。更不带 `preload`（要提交进浏览器预加载列表，撤不回来）。
2. **`Permissions-Policy` 刻意不列 `clipboard-write` / `web-share`**：
   站内「复制链接」用 `navigator.clipboard`（`app.js:682`）、「分享」用 `navigator.share`（:824），
   写进 `()` 等于亲手把这两个按钮弄坏。守护里有一条**反查**：
   从 `app.js` 数出站点真在用的能力，再断言头里没禁它们。

### 15.4 §八 CSP 下半（`script-src` / `style-src`）

最终值（`_headers` 与 `functions/_lib/security.js` 两份拷贝，守护逐字比对）：

```
script-src 'self' 'sha256-CJjlP287d9o8os05q1pTscyxju+Buc5X14AenQ46bUY=' https://challenges.cloudflare.com;
style-src  'self' 'unsafe-inline' https://fonts.font.im
```

- **两边走的两条路，是因为哈希在一侧真的做不到**：
  - `script-src` 用**哈希**（严格）：全站只有 **1 段**内联 `<script>`，它是源码里的静态文本、构建期不碰 ⇒ 哈希是稳定常量。
    ⚠️ 审计原文写的「3 段内联 `<script>`」**不准确**（把注释里提到的那些也数进去了）。
  - `style-src` 只能是**来源白名单 + `'unsafe-inline'`**：`index.html` 有 **19 处** `style="…"` 属性（运行期还有大量 `el.style.x=…`），
    而构建期还会把整张 `style.css` 内联成 `<style data-inlined>` —— 后者的哈希**随每次改样式而变**，写死在头里必然过期。
    这一条的价值是**收窄来源**（挡住任意外域样式表 / `@import` 外链），不是挡住内联样式。删掉 `'unsafe-inline'` 是白屏，不是加固。
- 🔴 **哈希必须按 LF 计算**：仓库 `core.autocrlf=true` ⇒ 工作区 CRLF、线上 LF。
  实测同一段脚本：LF 版 `sha256-CJjlP287…`（4834 字符），CRLF 版 `sha256-i6C6OEYy…`（差 79 个 `\r`）。
  在 CRLF 上算出来的哈希，线上就是**整段启动脚本被拒 ⇒ 白屏**。
- 🔴 **内联事件处理器不在哈希覆盖范围内**：兜底横幅那两个按钮原本是 `onclick="…"`，
  加了 `script-src` 之后会被拦掉 —— 而那恰好是"站点已经启动失败、只剩这个横幅能自救"的时刻。
  已改成 `addEventListener`（绑在那段有哈希白名单的内联脚本里）。`verify-security-headers.mjs` 现在断言「标记里没有内联事件处理器」。
- ⚠️ 断言前要**剥两层注释**：HTML 注释里会**提到** `<script>` 与 `onclick`（解释为什么不能用），
  `<script>` 块里的 JS 注释也一样。第一版只剥了 HTML 注释，于是被自己写的解释注释判红（假故障）。
- **验收链路（三层，`scripts/audit-csp.mjs`，18/18；`--raw-live` 在部署后跑）**：
  1. `[A]` 本地服务直接吐仓库里的 CSP ⇒ 页面正常启动、零违规、19 处内联 style 仍生效、兜底按钮无 `onclick`；
  2. `[B0]` **负向对照**：拿线上此刻的旧 HTML 配新哈希 ⇒ 浏览器**确实**报 `script-src-elem` 违规，
     并在控制台把**正确的哈希念出来**（这条比"断言失败"有用：修复线索不需要人肉猜）；
  3. `[B]` 线上**真域名** + 新 CSP + 新版内联脚本 ⇒ 零违规、浏览器自算哈希与 CSP 一致、
     Turnstile 的 `api.js` 仍被放行（`window.turnstile` 存在、挑战组件仍能挂载）。
- ⚠️ **Turnstile token 为 0 的 A/B**：headless 下拿不到 token。为分清"是不是 CSP 干的"，跑了对照组 ——
  **同 HTML + 线上现有 CSP 同样拿不到**（容器 661×72 已渲染）。⇒ 与本次 CSP 改动**无关**（沿用 §六 末尾那条未定性的旧账）。
- `verify-inline-css.mjs` 新增一条**闭环**断言：**构建产物**里那段内联脚本的哈希也必须命中 CSP 白名单 ——
  否则"源码对、CSP 对、构建动了字节"这种情况没人管（而且它也是第一版误红的地方，正好证明了这条的价值）。

| a11y 真浏览器（线上，双视口） | `node scripts/audit-a11y.mjs 1200 900` / `390 844` | ✅ **各 27/27** |

**最关键的一条证据是「不跑浏览器也能验的同步性」** —— 直接抓线上 HTML 算内联脚本哈希、
与服务器**同一次响应**下发的 CSP 声明值比对：

```
线上内联 <script> 段数: 1
  #1 长度=4834  实算=sha256-CJjlP287d9o8os05q1pTscyxju+Buc5X14AenQ46bUY=
     与服务器下发的 CSP 一致: ✅ 是（浏览器不会被拦）
```

这一条堵死了本次最大的风险（哈希不同步 ⇒ 整段启动脚本被拒 ⇒ 白屏），而且它**不依赖浏览器行为**，
所以比"页面看起来正常"更硬：白屏的判据必须在"能不能跑起来"之前先验"该不该被拦"。

> ⚠️ 复核这一条时**我自己的临时脚本连错两次**，都记下来因为它俩是同一个坑：
> ① 用 `<script(?![^>]*src=)[^>]*>([\s\S]*?)</script>` 数内联脚本，得到 **2 段**、且哈希**都不对** ——
> 因为 HTML 注释里**写着** `<script>` 字样（解释为什么不能用），正则从注释里那个 `<script>` 起匹配，
> 把真脚本整段吞进了前一个匹配。**剥掉 HTML 注释后才是 1 段**。
> ② 复验"线上标记里有没有内联事件处理器"时，先把 `<script>…</script>` 块剥掉再测 `<script>` 是否存在 ⇒
> 自己把要测的东西删了，得出"线上没有内联脚本 ❌"的假故障。
> 两次都不是代码的问题，是**验证脚本自己**的问题 —— 与 §十三 那次 `String.replace` 落在注释里同源。

## 十六、2026-09-17 事故：PBKDF2 迭代数 210000 让线上**注册全挂** —— ✅ 已修

> ⚠️⚠️ **本章的根因归因已被推翻并更正，务必先读 §十七。**
> 首次写作时我把根因写成「210000 超出 Pages Free 的 10ms CPU 预算 ⇒ 被平台终止（Error 1102）」。
> **这是错的。** 真因是 **workerd 对 PBKDF2 迭代数的硬上限 100000**，超过直接抛
> `NotSupportedError`。判据其实一直摆在那里 —— 超预算返回的是 **1102**，而实际返回的是
> **1101**（Worker threw a JavaScript exception）。
>
> 本章**刻意保留原文**（含 16.3、16.6① 里那段被推翻的推理），因为"我是怎么搞错的"本身就是教训；
> 但**凡与 §十七 冲突之处，一律以 §十七 为准**。

用户报「注册失败，请稍后重试」。**直接触发因素**是**上一批把 PBKDF2 默认迭代数从 100000
提到 210000** —— 这一点没错，事故边界就是它；错的是"它为什么会失败"的解释（见 §十七）。

### 16.1 先把"是哪一类失败"钉死，再去找原因

这句文案只出现在 `functions/api/register.js` 的**最外层 catch**（当时已改成通用文案）。据此逐条排除：

| 候选 | 排除依据 |
|---|---|
| 人机验证失败 | 那是 **403**，文案是「人机验证失败，请重试」 |
| 用户名重复 | 那是 **409**「该用户名已被注册」（本批刚加的翻译） |
| 平台级 5xx（HTML 错误页） | 前端 `await r.json()` 会抛 ⇒ 显示「**网络错误**」，不是这句话 |
| 请求体非法 | 实测会落进同一个 catch（见 16.5 ①），但前端发的 body 是 `JSON.stringify` 出来的，合法 |

⇒ 服务端 JS 真的抛了异常。**但当时 catch 已经把 `e.message` 换成通用文案（防泄漏），
响应里没有任何线索，日志也只在 Cloudflare 侧** —— 这就是本次排查最大的障碍，见 16.6 ②。

### 16.2 决定性判据：故障范围**精确等于**"用到新迭代数的那些路径"

这条判据不需要任何工具，只要问一句"为什么登录没坏"：

| 路径 | 用哪个迭代数 | 结果 |
|---|---|---|
| 老用户登录 | 存储串是 `salt:hash`，`parsePasswordHash` 给它的隐含迭代数是**写死的 100000** | ✅ 正常 |
| 登录时的"顺手升级" | `targetIterations()` ⇒ **210000** | ⚠️ 挂，但被 try/catch 包着且只记日志 ⇒ **看不出来** |
| **新注册** | `makePasswordHash(targetIterations())` ⇒ **210000** | 🔴 **用户可见的失败** |

**故障集合 = {用到 210000 的路径}**，一个不多一个不少 —— 这正是"迭代数"这个单变量的特征。
本批相对上一版的**唯一行为差异**也正是它。

### 16.3 官方事实 + 实测数字

Cloudflare 官方 limits（`developers.cloudflare.com/workers/platform/limits`）：

| | Workers / Pages Free | Workers Paid |
|---|---|---|
| CPU time per HTTP request | **10 ms** | 5 min（默认 30 s）|
| 超限表现 | **Error 1102**（`Worker exceeded resource limits`）——**不是慢，是整条请求被终止** | 同左 |

本机实测：`100k = 30ms` / `210k = 60ms` / `600k = 171ms`（CPU 时间）。

> ⚠️ **别拿墙钟当理由**：`makePasswordHash(210000)` 在本机测出 **122ms 墙钟**看着"也不慢"，
> 但限额与计费只算 **CPU 时间**，I/O 等待不算。这两个数字差了一倍，很容易把人骗过去。

> 🔴 **上面这些数字全部属实，但它们并没能支撑当时那个结论**（更正见 §十七）。
> 它们是"CPU 预算"这条路上的证据，而真因在**另一条路**上（平台硬上限）。
> **数据为真 ≠ 推断为真** —— 这是本章最大的教训。
> 还要注意：本机 Node 的 `crypto.subtle` **没有** workerd 那个 100000 上限，
> 所以**本地无论测出什么数字，都测不出边缘的那条硬边界**。

### 16.4 修法与真机验证

- `PBKDF2_DEFAULT_ITERATIONS` 退回 **100000**（= 本批之前长期在线上跑的值），并把事故写进 `auth.js` 顶部。
- 存储串仍带迭代数（`pbkdf2$<iter>$…`），所以**将来档位升级后仍可安全上调**，不用重置任何密码；
  灰度优先用 `PBKDF2_ITERATIONS` 环境变量（不用重新部署就能回滚）。
- **真机验证（只有真人能过 Turnstile 挑战）**：用户注册 → 「✅ 注册成功，已登录」；已有账号登录 → 正常。✅

### 16.5 顺带揪出的两个真问题（都不是根因，但都真实存在）

**① `register.js` 缺 `request.json()` 的内层 try**（`login.js` 一直有）

请求体不是合法 JSON 时它会抛进最外层 catch ⇒ 把「客户端发了坏请求」报成
**500「注册失败，请稍后重试」**，既误导用户去重试，也让排查看不到真因。已补 **400「请求格式错误」**。

> 讽刺的是：这个缺陷在排查中一度被我当成"不依赖人机验证就能触发 catch"的**探针**用
> （发一段非 JSON，看响应里有没有诊断码，借此确认新版本上线）—— 结果它自己就是一条待修的 bug。

**② `verify-login-hardening.mjs` 把判据写成了「默认迭代数 == 210000」**

守护因此**把一个错误的值锁死**了：改回 100000 反而判红。已改为盯**不变量**
（默认值落在合法区间、且不超过实测可用上限 `PBKDF2_SAFE_MAX`，并附上调前必须真机验证的说明）。

> 连带修好它的一条**负向自证**。故障①（"忽略存储串里的迭代数"）原本靠
> **"默认值恰好 ≠ 样本值 100000"** 才变红；默认值退回 100000 后两者撞上，
> 损坏版与正确版算出的结果**完全相同** ⇒ 判据恒绿、**自证静默失效**。
> 也就是说：**这一条唯一守卫着"直接改迭代数会锁死存量密码"的断言，其可观测性建立在巧合上。**
> 现在改成动态避开默认值，并**补了一条正向对照**确保"变红"不是因为样本无效。
> ⚠️ 还踩到一个更隐蔽的：用老格式 `salt:hash` 配 60000 造样本会**假红** ——
> 老格式的迭代数是**写死的 100000**，所以那个串本身就没有效，判据红得毫无意义。
> 负向自证必须同时证明"**对照件本身是有效的**"。

### 16.6 三条教训

**① 受平台硬约束的常量，不能按教科书建议值调。**（结论成立，理由已按 §十七 更正）

OWASP 建议 PBKDF2-HMAC-SHA256 用 210000~600000 —— 但那前提是**你能决定它跑在什么运行时上**。
这里跑在 workerd 上，**它对 PBKDF2 迭代数的硬上限就是 100000**（§十七 实测：100001 直接抛
`NotSupportedError`，平台自己在 message 里报出了上限值）。**"更安全"的建议值在这里让功能完全不可用**，
而且失败形态是**抛错**、不是变慢 —— 所以压测、本地跑、看墙钟，一个都发现不了，只能真机验。
凡是"调大一个数字"的改动，先问：**它的上限由谁决定？我能不能测出来？**

**② `catch` 把原因吞干净，等于给自己埋雷。**
"不回显 `e.message`"（防泄漏表结构）是**对的**；但连**日志里**都没留下可检索的分类，
就变成"线上只知道坏了、不知道坏在哪"。现在的做法：响应体保持通用文案，**日志里带白名单分类码**
（`register failed [E1-cpu]: …`），既能直接在 Cloudflare 日志里搜，又不泄漏任何原始信息。

**③ 定位线上故障时，"一次部署同时做修复与诊断"比"先诊断再修"更快。**
本次把**回退迭代数**（大概率修复）和**诊断码**（万一没修好也能定位）放进同一次提交，
用户只需重试一次就能二选一收敛。纯诊断版要用户多跑一轮，纯修复版赌错了就白等一轮。

### 16.7 仍未做（诚实标注）

- ⚠️ **强度停在 100000（= 平台硬上限），低于 OWASP 建议量级。**
  ✗ 原文写「升级到 Workers Paid 档（CPU 预算 30 s）即可上调」—— **这个承诺不成立**：
  上限是 workerd 的**校验规则**，不是 CPU 预算的推论。issue #1346 里官方明确说
  「配置机制已落地，但**生产环境仍保持该限制**，尚无时间表」。
  ⇒ 唯一可靠的做法仍是**实测**：改了之后在真边缘跑一次 `> 100000` 的哈希，能过才算数。
- ⚠️ 两条 D1 迁移仍需手工执行（`migrate-login-attempts.sql` / `migrate-guestbook-day.sql`），见 §十五 末。
- ℹ️ 排查中确认了一个长期疑点：**「注册框真实挑战 token 恒为 0」是探针环境的限制，不是站点缺陷** ——
  headless（乃至把窗口摆到屏幕外）都过不了 Turnstile 挑战，同页留言墙在同样条件下也恒为 0。
  站点侧的真实证据是**用户真机能注册成功**。

## 十七、2026-09-17 复测：真因是**平台硬上限 100000**，不是 CPU 预算 —— §十六 归因更正

### 17.1 起因

用户问：**「CPU 资源 10ms 预算，按存储串里的 100000 够吗？」**

这个问题的前半句正是 §十六 那个结论的再表述。要回答它需要一个**边缘上的直接判据**，
而 §十六 手里只有间接推理（210000 挂 / 100000 通 + 官方 10ms 文档 + **本机 Node 的墙钟**）。
本机 `crypto.subtle` 与 workerd 并非同一实现，**拿它的数字去比边缘的预算本身就不严谨**。

### 17.2 决定性实验：给只读端点加临时探针

`GET /api/config?__hashdiag=<iterations>` —— 在**真实边缘 isolate** 里跑一次
`makePasswordHash`（与注册路径**同一个函数**），回传 `{ ok, n, errName, errMsg, perfRaw }`。
只读、单次只算一个 n、限幅 10000–400000、显式 `no-store`。**拿到数据后已拆除并重新部署。**

### 17.3 结果（第一手 —— 平台自己报出了上限）

| iterations | 结果 |
|---|---|
| 100000 | ✅ 3/3 成功；另**连打 25/25 全部成功**、零平台终止 |
| **100001** | ❌ 3/3 抛 `NotSupportedError`：`Pbkdf2 failed: iteration counts above 100000 are not supported (requested 100001).` |
| 100500 / 101000 / 110000 / 125000 | ❌ 同上（message 里的 requested 值随之变化）|

**边界精确到 100001，且平台在错误 message 里自己写明了上限值。** 这不是超时、不是资源超限 ——
是**在进入计算之前**就被拒绝了。

两条辅证：

- 直接 `curl` 一个超限值，响应是 **HTTP 500 + `error code: 1101`**（*Worker threw a JavaScript
  exception*），**不是 1102**（*Worker exceeded resource limits*）。§十六 的归因就是漏看了这个数字。
- `performance.now()` 在这个环境**不可用于计时**：同一请求内前后两次读数**完全相等**
  （`perfRaw=[1789620269912,1789620269912]`）。所以"边缘耗时"这类数字不能由它得出 ——
  平台为缓解旁路攻击故意把计时器做粗了。**想量边缘成本，只能用"过 / 不过"这类离散判据。**

### 17.4 平台为什么这么设计（官方原话）

workerd issue [#1346](https://github.com/cloudflare/workerd/issues/1346)：

> "Since our CPU time-limiting code **cannot interrupt BoringSSL in the middle of running PBKDF2**,
> we have to limit the iterations **upfront**."

即：**PBKDF2 是一段平台无法中途打断的计算**，所以没法用"超时掐断"兜底，只能**事前**把迭代数
卡在 100000。这个值是按**当年 50 ms 总限额**定的，与今天的档位（Free 10 ms / Paid 30 s）
**没有可推导的对应关系**。issue 里同时说明：配置机制已在 workerd 落地，但**生产环境仍保持该限制，
无时间表**。

⇒ 这也解开了 §十六 里一个隐含矛盾："为什么 100000 明明算得不快却还能成功"。
它跑得并不便宜，只是**不受 CPU 限时中断**，所以能跑完。

### 17.5 对那个问题的正面回答

1. **够。** 100000 在真边缘连打 **25/25 全部成功**，且**无偶发失败** —— 若踩在预算边缘，
   会零星失败。它同时是当前可用的**最大值**，也正是默认值。
2. **但"10ms 预算"这个前提本身指错了方向**：制约它的是 workerd 的 **100000 硬上限**，
   不是 CPU 预算。在这条路径上 10 ms 并未成为瓶颈（PBKDF2 不可被中断）。
3. **不需要为"留余量"而下调**：100001 被拒是**规则**拒绝，不是**性能**拒绝。
4. **上限能否放宽不由我们决定** —— 既不是改数字、也不是升档就能保证，**只能实测**。

### 17.6 教训：**数据为真，推断为假**

§十六 里每一个事实都是真的：官方 10ms 文档为真、本机实测数字为真、"210000 挂 / 100000 通"为真、
"故障集合精确等于用到 210000 的路径"也为真。**但把它们串起来的那个结论是错的。**

问题在于：**当时有两个假设都能解释全部观察** ——

| 假设 | 解释"210000 挂、100000 通"？ | 解释"只有注册坏"？ |
|---|---|---|
| A：CPU 预算超限（1102） | 能 | 能 |
| B：平台硬上限抛错（NotSupportedError） | 能 | 能 |

我没有去找**能把它们分开**的观察，而是挑了"更合理"的那个（"10ms"这个数字当时刚查到，很醒目），
并用**第一手证据的语气**把它写进了文档、代码注释和守护脚本。

**能分开它们的判据一直摆在那里**：`curl` 一次就能看到是 **1101 还是 1102** ——
而这正是我第一次真正去抓响应体时**一眼看到**的东西。

> **规则**：当两个假设都能解释你手上的全部观察时，**不许在它们之间选**。
> 去找那个"在 A 下必须 X、在 B 下必须 Y"的观察。找不到就先写成**待定假设**，
> 不要写成结论 —— 尤其别写进代码注释，那会让错误活得很久。

> **推论**：`Error 1101` 与 `Error 1102` 是两个完全不同的事实（**JS 抛错** vs **资源超限**）。
> 排查时**先抓响应体确认是哪一个**，不要从"用户看到的文案"直接跳到原因。

### 17.7 留下的可复用手法

- **在真实边缘量成本**：临时只读探针 + 边界扫描（100000 / 100001 这种相邻取值最锋利）。
  判据要用**离散的"过 / 不过"**，不要指望计时器（`performance.now()` 在 Workers 里恒等）。
- **探针必须回传 `e.name` / `e.message`**：这是区分"平台终止请求"（拿不到响应体）
  与"我们的 JS 抛错"（能捕获）的**唯一**办法。
- **临时探针的收尾是流程的一部分**：它未认证即可触发一次昂贵计算，等于一个 CPU 放大面。
  本项目已形成固定动作 —— 用完 `git checkout <干净版> -- <文件>` 还原，再单独部署一次。

## 十八、注册表单加「确认密码」框

### 18.1 四个刻意的设计点

| 点 | 做法 | 理由 |
|---|---|---|
| **位置** | 紧贴密码框，但在 `#registerTurnstile` 容器**之前** | Turnstile token **一次性**。若先取 token 再校验一致性，用户每输错一次都要重新过一遍人机挑战 |
| **不发给服务端** | `/api/register` 仍只收 `password` | 它对安全性**零贡献**（攻击者填两遍相同的即可），纯粹是防手滑的浏览器侧约束 ⇒ 服务端不需要知道 |
| **autocomplete** | 也用 `new-password` | 密码管理器据此把两个框填成同值 |
| **不一致时** | 报错 + **清空第二格并把焦点移过去** | 让用户直接重输，不必自己找是哪一格填错了 |

顺带给密码框补了 `minlength="6"`（与「至少 6 位」的占位提示一致）。原生约束在 `submit` 事件
**之前**生效，所以它确实能省掉一次请求。

### 18.2 顺手补掉的一处不对称

`login` 一直有 `loginBusy` 防双击，`register` 没有。而注册**更**怕重复提交：
**每发一次就消耗掉一个一次性 Turnstile token**（第二次必然 403，用户得从头再过挑战）。
已补 `registerBusy`，两处统一用 `try/finally` 收尾。

### 18.3 守护

### 18.5 实测揪出的**既有遗漏**：认证弹窗输入框的触屏适配

项目里 `.remember` / `.share-btn` / `.share-link-copy` / `.ts-fallback-retry`
都在 `@media (pointer: coarse)` 里补过 `min-height: 44px`，
**唯独登录/注册弹窗的输入框漏了** —— 实测 **43px**（12+12 padding + 1+1 边框 + 17 行高），差 1px。

修法：在文件最末尾**单开**一个 `@media (pointer: coarse)` 块，不碰上面那些已有断点块
（它们各自有守护断言）。放末尾是**必须**的：同优先级规则靠**后写**取胜（`@media` 不增加特异性），
放别处会被后面的断点吃掉 —— 这是本项目踩过的坑。

**同视口 A/B 对照**（1024×768，只切换触摸模拟；此处 `max-width:980px` 不命中）：

| | `pointer:coarse` | `max-width:980px` | font-size | min-height | 输入框高度 |
|---|---|---|---|---|---|
| 触屏 | **true** | false | **16px** | **44px** | **[44,44,44,44]** |
| 鼠标 | false | false | **15px** | auto | [43,43,43,43] |

#### ⚠️ 一处必须更正的表述（写在先一个提交里）

提交 `cc0ef81` 里我写了「font-size 15px < 16px ⇒ iOS 聚焦放大，**实测**发现」。
**"实测"这两个字不成立** —— 我从没量过字号，那是看到基样式写着 `15px` 之后**推断**出来的。

A/B 表明：窄屏下 `.auth-form input` **本来就是 16px**（由 `@media (max-width:980px)` 的
「触屏输入框统一 ≥16px」块兜着）。新规则真正起作用的是**宽屏触屏**（iPad 横屏等
`max-width:980px` 不命中的场景）—— 那里确实是 15px → 16px。
**结论没变（这条规则有用），但理由必须换掉。**

### 18.7 探针自己犯的三个错（都记录在案）

- **假故障**：用 `/\/api\//` 匹配全部 URL，把 Turnstile 向 `challenges.cloudflare.com`
  发的内部请求（路径含 `/turnstile/.../api/normal`）也算成了"我们发的"。
  ⇒ 限定**同源**，并加一条**方法自证**（"同源 /api/ 过滤器确实抓得到请求"）——
  否则"一个都没发"这条判据会退化成恒真的摆设。
- **假失败**：`querySelectorAll("input")` 把 Turnstile 注入的隐藏 input（高度 0）也算了进去，
  量出 `[43,43,43,43,0]`。⇒ 滤掉 `type=hidden` 与不可见元素。
- **假失败（第三次）**：`Emulation.setDeviceMetricsOverride({mobile:true})` **不会**让
  `(pointer: coarse)` 命中，必须另发 `Emulation.setTouchEmulationEnabled`。
  少了这一句，CSS 已经上线却仍量到 43px —— 会把「已修好」误判成「没修」。
  ⇒ 探针现在把 `matchMedia("(pointer: coarse)").matches` 与 computed
  `font-size` / `min-height` 一并打出来：**断点到底命中没有，必须是可观测的证据，不能靠推测。**
