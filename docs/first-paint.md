# 首绘与「打开文章」的关键路径

> 「不止农历挂件卡，文章和左侧列表也会卡」—— 2026-09-15 的排查与修复。
> 相关守护：`scripts/verify-first-paint.mjs`（83 项）、`scripts/verify-inline-css.mjs`（样式表内联，20 项）；
> 复测工具：`scripts/perf-probe.mjs`（只需时序）、**`.diag/first-paint-probe.mjs`（要判 FCP/CLS 与渲染是否变化时用它）**。
> 用法速查：`--link` / `--inline` / `--both`（本机受控 A/B，`--mobile`、`--rtt=`/`--kbps=`、`--neg` 负向自证）、
> `--live [--rounds=N]`（**线上 A/B**：真域名，用 Fetch 把线上顶替回旧形态当对照组，ABBA 顺序）。
> 封面单独成篇：**阻塞与否、为什么不加载、怎么少下一次 → `docs/cover-delivery.md`**
> （封面不是渲染阻塞资源，但它是 LCP；同一张图曾占两个 URL、各下一份）。

## 怎么量的（别再靠猜）

装不了 puppeteer/playwright（要下 ~500MB Chromium，国内很慢），改为**直接驱动本机 Edge**：
`scripts/perf-probe.mjs` 用 CDP 打开页面，取 `performance.getEntriesByType()` 的真实数据。

```
node scripts/perf-probe.mjs https://blog-6p3.pages.dev/            # 冷缓存（全新 profile）
node scripts/perf-probe.mjs "https://blog-6p3.pages.dev/?post=<slug>" --warm
```

它同时会抓**控制台错误与未捕获异常** —— 这个项目的 P0 事故（TDZ 被 catch 吞掉）就是
「功能全错、控制台安静」，所以每次探针都顺手看一眼。

⚠️ **不要用 curl 的耗时直接下结论**：每次 `curl` 都要重新握手，跨境 TLS 就要 0.5~1.1s，
会把每个请求都算大 0.6s 左右。实测同一份 `posts.json`：curl 报 790ms，浏览器只用了 **179ms**
（复用了 HTTP/2 连接）。两者差的不是网络，是握手。

## 四个真因（按影响排序）

### ① 正文里的 base64 内嵌图（最大，也是「打开文章卡」的主因）

`generated/posts/<slug>.json` 直接用了 `row.body` —— 而正文里的图常是 base64 内联的。

| | 不含内嵌图的文章 | 含内嵌图的文章 |
|---|---|---|
| 篇数 | 9 / 16 | **7 / 16** |
| 平均详情体积 | 0.8KB | **530KB** |
| 最大一篇 | — | **1,148,543 字节（1.14MB）** |

一篇正文只有 68 字的文章，详情也有 151KB（全是那张图）。跨境网络下拉 1.1MB 的 JSON，
表现就是「点开文章愣好几秒」。

**改法**：`materializeBodyImages()` 早就写好了（把 base64 抽成
`/generated/body-images/<内容哈希>.<ext>`），只是**结果只喂给了爬虫片段**。
现在详情快照也用它 → 详情只剩几 KB，图片走独立文件：可被浏览器长期缓存（`immutable` 一年）、
可懒加载、也不再和正文抢同一个响应体。

### ② 两次纯装饰的请求挡在正文渲染之前（~600ms，且**永不缓存**）

`openPost()` 原先的顺序是：

```
静态详情(563ms 就到了) → await /api/me → await /api/posts/view → 才渲染(1171ms)
```

`/api/me` 只用来决定显不显示「编辑/删除」按钮，`/api/posts/view` 只是阅读数 +1 ——
与正文内容毫无关系，而且两者都是 `no-store`（**永远不走缓存**），所以**每次打开文章都要等**。

**改法**：先渲染正文，再由 `patchPostMeta()` 异步补齐。
另外 `/api/me` 实测会被请求**两次**（启动一次、打开文章一次），改用 `ensureSession()` 去重复用同一个 promise。

实测：正文 1171ms → **约 570ms**（暖缓存）。

### ③ 跨站渲染阻塞样式表（字体，冷缓存 ~400ms）

`<link rel="stylesheet" href="https://fonts.font.im/css2?...">`
未压缩 **339KB / gzip 91KB / 303 条 @font-face / 101 个子集**，是**跨站**资源，
而 `<link rel=stylesheet>` 会阻塞首绘 —— 于是首屏所有内容（文章、侧栏、挂件）一起等它：
实测冷缓存 FCP 从约 900ms 被拖到 **1296ms**。

**改法**：从 `index.html` 移出，由 `app.js` 在首绘之后（两层 rAF）动态注入。
动态插入的 `<link>` 不参与渲染阻塞，字体到达后由 `font-display:swap` 自然替换。

- ⚠️ **不要用 `media="print" onload="this.media='all'"`**：小米/360 兼容模式对该切换支持不良，
  会导致样式表永远不生效（项目已因此回滚过一次，见 `index.html` 里 style.css 上方那条注释）。
- ⚠️ 注入的 link 必须带 `data-optional="1"`，否则它加载失败会触发 `index.html` 的全局 error 监听、
  弹出「资源加载失败」横幅 —— 字体下不来不该吓用户。

### ④ 本机 CSS 阻塞首绘（冷缓存 ~600ms，2026-09-17 已修）

`<link rel="stylesheet" href="assets/style.css">` 108KB（br 32.9KB）是**渲染阻塞资源**，
浏览器要等它到齐才肯画第一帧。而它是**本站资源**，所以这 600ms 全是「一个跨境往返 + 传一个包」，
不像字体那样还有第三方的不可控因素。

**改法**：`build.mjs` 在构建期把它**内联进 HTML 外壳**（`scripts/lib/inline-css.mjs`）。
源码 `index.html` 仍保留外链形态 —— `assets/style.css` 是唯一样式来源，本地开发、`--local` 探针、
所有 `verify-*.mjs` 读到的都还是外链形态；内联只发生在构建产物里。

**为什么不是常规做法**：

- 🚫 `media="print" onload` / `rel=preload onload` —— 见 ③ 的雷区，onload 系切换在小米/360 不可靠。
- 🚫 拆 `critical.css` + 首绘后由 JS 注入 rest —— 收益只多 ~12KB，却要背 FOUC/CLS 风险，
  而且样式一旦必须靠 JS 才到位，脚本一挂页面就裸奔。
- 内联的账（本机 brotli，与 CF 同档位 q4 复现）：`style.css` 单独传 **32889 B**；
  合进 HTML 后整份只涨 **24272 B** ⇒ **传输字节基本持平，少了一整个往返**
  （实测首屏总字节 48069 → 46066 B）。因为站点只有**一个 HTML 外壳**
  （SPA；文章页是边缘函数往同一份 `index.html` 里注入正文），内联只影响一个文件。
- 代价：`/` 的策略是 `max-age=0, swr=300`，重复访问走 304 复验、不传正文，
  所以「CSS 不能再单独缓存」的实际代价是**仅在某次部署后首次回访时多下 ~26KB**。

### 怎么证明它真的更快、而且没把渲染改坏

工具：`.diag/first-paint-probe.mjs`（真浏览器 + CDP，**带限速**）。三件事必须钉死才敢下结论：

1. **限速**：本机到本机几乎零延迟，不限速两种模式测不出差别。用 `emulateNetworkConditions`
   取 RTT 150ms / 200KBps，先要求**外链模式复现线上量级**（实测 843ms，线上 658ms）——
   模拟不具代表性时，探针会直接提示「结论不能外推」。
2. **本地服务必须压缩**：线上是 br 传输（style.css 32889 B），不压缩会多传 80KB，
   把对照组凭空夸大近 400ms。
3. **两侧必须到达同一内容状态再比**：`/generated/posts.json` 466KB（含 base64 封面），
   节流下到达时机不稳 —— 实测踩到「外链模式渲染 0 张卡片、内联 8 张」，
   那是测试台不等价，不是改动的影响。现在探针会等卡片渲染出来，并把「两侧卡片数/元素数一致」
   本身写成断言。

结果（桌面 1440×900 与移动 390×844 各一轮，卡片的几何/计算样式/文档高/规则数逐项比对）：

| | 外链阻塞 | 内联 |
|---|---|---|
| TTFB→首绘 增量（桌面） | 843ms | **425ms** |
| TTFB→首绘 增量（移动） | 853ms | **414ms** |
| style.css 请求数 | 1 | **0** |
| 首屏总字节（doc+css） | 48069 B | **46066 B** |
| 整页布局指纹（桌面 629 元素 / 移动 528 元素） | 3549702810 / 118277715 | **逐项相同** |
| 控制台错误 | 0 | 0 |

负向自证：`--neg` 把内联那一步拆掉（只改临时副本）后，收益消失（843 vs 881ms）、
5 条断言变红、退出码 1 ⇒ 这个收益来自内联本身，不是「跑第二次更快」的顺序假象。

#### 线上复量（不能只信本机受控）

线上没法「改代码再部署一次」来做对照（真实链路条件不可复现，而且资源与域名绑定），
所以用 CDP `Fetch` 把线上首页**顶替回旧形态**：同域名、同一次会话、同一台机器，只换样式表投递方式。
顺序取 **ABBA**（新·旧·旧·新）抵消单调网络漂移（`node .diag/first-paint-probe.mjs --live [--rounds=N]`）：

| 线上 A/B（**8 轮 = ABBA×2**） | 新形态（内联） | 旧形态（顶替回外链） |
|---|---|---|
| TTFB→首绘（各轮 / 均值） | 217, 226, 212, 165 / **205ms** | 1086, 1057, 796, 1056 / **999ms** |
| `assets/style.css` 请求 | 0 | 1（线上真取，br ≈33.6KB） |
| 全页布局指纹 | `3658275972`（677 元素 / 9 卡） | **相同** |
| CLS 各轮 | 0.0541 ×4 | 0.0168 ×3, 0.0541 ×1 |

⇒ 线上省约 **794ms**。字节 br 后持平（新 **46396 B** vs 旧 **48924 B**）。
（另有一遍 4 轮的：新 163ms vs 旧 983ms、省 819ms —— 两遍一致。）
⚠️ 顶替的响应只能发明文（试着加 `Content-Encoding: br`，Chrome 不解码，页面只剩 14 个元素），
所以 live 模式里「主文档传输字节」一列**不可比**；探针改为用**真数字复算** br 后的首屏总字节
（新形态本地 br q4 复算、旧形态另加线上 `style.css` 的真实 br 字节）。

#### ⚠️ 线上 CLS 从 0.0168 升到 0.0541 —— 是「提前暴露」，不是重排

- 两形态**全页布局指纹完全相同** ⇒ 渲染结果没变，不存在「样式晚到导致重排」（这正是本次判据要防的）；
- 位移源定位到 `assets/app.js:1277`：`loadPosts()` 先塞 **4 张骨架卡**进 `cardGrid`，
  `fetchAllPosts()` 回来后 `renderCards()` 再换成真实内容 —— 这是**改动前就有**的位移，
  旧形态自己也抽到过 0.0541，说明它不是某一形态的属性；
- 以前大多看不见，是因为旧形态首绘在 ~999ms，那次替换通常落在首绘**之前**（没画出来的位移不计分）；
  现在首绘提前到 ~205ms，它就稳定暴露在用户眼前了；
- 0.0541 仍在 Core Web Vitals 的 good 区间（< 0.1），而首绘快了约 794ms，净收益为正。
  **要彻底消掉它得动骨架的尺寸/数量，属视觉改动，本次没做**（见 `optimization-audit-2026-09-16.md` §十四）。

⚠️ CLS 在这个站是**双峰**的（0.0541 / 0.0168），取决于那次骨架替换落在计分窗口哪一侧。
所以**别拿单轮互比**（第一次跑就踩了：旧形态那轮正好抽到 0.0168，于是报出一个假回归）。

### ⚠️ 由此暴露的一个既有布局问题（顺带修掉了）

移动端第一次跑时 **CLS 反而变差：0.0464 → 0.0812**。逐帧抓下来是顶栏在首绘后**塌 33px**
（`HEADER.topbar` 93 → 60），把下面所有东西带上跳。

根因与样式表投递无关：`.layout` 有 `min-height:100vh`，而 grid 的 `align-content` 默认是 `stretch` ——
「内容还没渲染、页面总高不足一屏」那段时间里每一行都被拉高去填满视口，topbar 那行从 60 被撑到 ~93；
内容一到、总高超一屏，行又缩回自然高度。**外链模式同样会做这件事，只是它首绘太晚，把这一跳藏在了首绘之前**
（这也意味着：暖缓存下今天其实能看到这一跳，只是没人量过）。

改法：`.layout { align-content: start; }`。修完移动端 CLS 回到 **0.0464**，
且**内容加载完之后的整页布局指纹逐项不变**（桌面 3549702810 / 移动 118277715，改前改后一致）。
`.sidebar` 在桌面是 `align-self:start` + sticky、`.rightbar` 有确定高度、移动端抽屉是 `position:fixed`
⇒ 三列都不依赖这一拉伸，所以没有连带观感变化。

### 顺带：骨架屏的微光动画

`.skeleton` 原来动 `background-position`（400% 宽的渐变 → 每帧重绘整块元素），
而骨架屏会连续显示数秒（等 `posts.json` / 封面图）。改成覆盖层 + `transform` 位移，
只走合成器。**这条是预防性的**：本机实测没有长任务掉帧证据，属于「顺手消掉的隐患」。

## ⚠️ 随之而来的硬约束：详情快照的 body 是构建产物

`generated/posts/<slug>.json` 里的 `body` 现在含 `/generated/body-images/…` 路径，
而**编辑器是从快照加载文章的**（`openCompose`）—— 拿它预填再保存，就会把产物路径写回 D1，
而 `generated/` 不入库、每次构建都可能改名甚至消失 → **原始图片永久丢失**。
这和封面那次是同一类事故（`3afafdd`），所以按同样的方式做了两道防线：

1. **前端**：点「编辑」一律从 `/api/posts/detail` 取**原始**正文再进编辑器；
   取不到就**不进编辑器**（宁可让用户重试，也不能拿快照正文顶替）。
2. **后端**：`manage.js` 加了绊线 `isBuildArtifactBody()` —— 正文里出现**图片形式**的
   `/generated/body-images/` 引用就直接 **400**。

第 2 条刻意选择「响亮失败」而不是像封面那样静默保留旧值：正文是用户这次真正在编辑的东西，
静默保留会让他以为改动生效了、实际白改。
判定只看**图片引用**（markdown `![]()` 或 `<img src=>`），不做全文匹配 ——
本博客就写技术文章，正文里完全可能出现这条路径的文字示例，全文匹配会误伤、把作者卡在保存不了。

### 一个已知取舍

`/generated/body-images/*` 是内容哈希命名、`immutable` 一年，但**旧文件会随新部署消失**。
若作者替换了某张图，而某个客户端还握着 SWR 期内的旧快照（最长约 24h），那张图会 404。
影响面很小（只有作者改图时、且只有旧快照），与封面原有的行为一致。
新发布的文章若还没构建，走 `/api/posts/detail` 降级路径，返回的是**原始**（含 base64）正文 ——
功能正常，只是没有这份优化。
