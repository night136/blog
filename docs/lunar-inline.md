# 农历：从 426KB 外部库改为内联数据表

> 本文取代 `docs/lunar-load.md`。那篇讲的是「外部库加载失败怎么补救」（看门狗 + 退避重试 + 可见入口）；
> 现在外部库**已经不存在了**，整个失败类别随之消失，故那套机制连同文档一起下线。

## 结论

| | 改前 | 改后 |
|---|---|---|
| 农历数据来源 | `assets/vendor/lunar.js`，426KB（br 约 110KB） | 内联在 `assets/app.js` 里的两张表 |
| 首屏额外下载 | **约 110KB**（独立请求） | **0**（与 app.js 同一请求） |
| app.js 体积 | 113.8KB（gzip 39.8KB） | 130.9KB（gzip 41.8KB） |
| **首屏净变化** | — | **约 −108KB** |
| 加载失败的可能性 | onerror / 挂起 / 超时 / 刷太快掐断下载 | **不存在**（没有下载这回事） |
| 需维护的机制 | 状态机 + 看门狗 + 退避重试 + 预加载 + 窄屏按需加载 | 无 |
| 窄屏能否看到农历 | 需先点「查农历」下载 110KB | 直接显示 |

原来那三条叠加的故障原因（空闲懒加载 → 失败静默 → 刷新掐断下载）**一条都不再成立**，
因为农历数据和 app.js 是同一个文件、同一个请求。用户报的「连续刷新农历一直空」属于这一类。

## 为什么是「表」而不是「公式」

一开始想用经典的节气公式（24 个分钟偏移 + 回归年长度）把数据压到几十字节。实测**不可行**：

```
对照 lunar.js 逐日全量比对 1900–2100 的 4824 个节气：
  公式法不一致 240 处（4.98%）—— 1902 冬至、1909 大寒、1910 立春与清明、1911 立夏、1912 小寒与寒露 …
```

差一天对「今日节气 / 明日节气」这种展示是硬伤（会把 9 月 23 日的秋分说成 9 月 22 日）。
农历的闰月与大小月更是没有可靠公式，必须查表。所以最终方案是**从旧库导出表**。

## 数据与算法

`assets/app.js` 里 `LUNAR-INLINE-START` / `LUNAR-INLINE-END` 之间的整段（约 220 行）：

- **`LUNAR_YEAR_INFO`**（202 项，1899–2100）每年一个整数：
  `低 4 位` = 闰月月份（0 = 无闰月）；`bit 16` = 闰月是大月；`bit 15..4` = 正月..腊月是否大月
- **`LUNAR_JIEQI_DAYS`**（4872 字符）自 1899 年起每年 24 个节气日。第 n 个节气（小寒=0）固定落在
  `floor(n/2)+1` 月，所以只存「日」；`'0'-'9'` 表示 1–9 日，`'a'-'n'` 表示 10–23 日
- **算法**只做日数推算：以「农历 1900 年正月初一 = 公历 1900-01-31」为锚点算天数序号，
  正推得公历、反推得农历月日。干支/生肖按 `(y−4) % 10/12` 算术得出，无表

原始约 6.3KB，**gzip 后 904 字节**（对比原来的 br 约 110KB，约 122×）。

两个容易踩的点，已在代码注释与本脚本中钉住：

1. **日期运算必须走 `Date.UTC`**。用本地时间会被夏令时/时区推成 0.5 天，日界随之漂移。
2. **闰月的位置**：闰月紧跟在同名平月之后（`1, 2, 闰2, 3, …`）。算「该月之前有多少天」时，
   查闰月本身要**含**同名平月的天数、但不含闰月天数；查其后的平月要**含**闰月天数。
   写错的话只有闰年出错、且只差一个月——非常容易被忽略（本文档的负向验证专门盯这一点）。

## 正确性怎么保证

**不是靠「看起来对」，是靠对旧库做全量比对**：

- `scripts/lib/lunar-digest.mjs` 定义「摘要」格式（逐日 + 逐月拼串后 sha256）。
  生成基准与校验共用同一份格式化逻辑，避免两份实现漂移导致假失败
- `scripts/fixtures/lunar-golden.json` 是从旧库生成的黄金基准：
  **逐日 73445 条 + 逐月 2498 条 = 75943 条**记录、201 个正月初一、147 条逐字段抽样
- `scripts/verify-lunar-core.mjs`（71 项）把内联代码块整段抽出来真跑，逐条比对：

| 小节 | 内容 |
|---|---|
| [1] | 块存在、可求值、不引用任何外部全局（`Lunar`/`window`/`document`…） |
| [2] | 外部依赖与旧机制已彻底移除（含「注释除外」的剥注释比对） |
| [3] | **全量摘要比对 75943 条**（耗时约 400ms） |
| [4] | 201 个农历正月初一（年边界最易错位处） |
| [5] | 147 条抽样逐字段比对（失败可定位到具体日期） |
| [6] | 内部一致性：73767 次往返自洽、月长与公历跨度相符、月份首尾相接、闰年 74 个 |
| [7] | 范围边界（1899-12-01 / 2100-12-31）与超范围返回 null 的降级 |
| [8] | **8 组负向验证**（改坏算法 → 摘要必须变红）＋ 纯净性断言的负向 |
| [9] | 前端配套（窄屏 CSS、`.lunar-sx` 不是死代码、体积台账） |
| [10] | **行为验证**：DOM 沙箱里冻结时钟真跑 app.js，断言渲染出的 HTML |

[10] 用固定时钟渲染了几组真实日期，把「算得对」升级成「画得对」：

- `2026-09-15` → hero 行 `🗓 丙午年（马）八月初五 · 申时 15:52:05`；侧栏 `8 天后 · 秋分`；
  月历 7 表头 + 35 格（5 整行）、今天恰好高亮 1 格且是「公历 15 / 农历初五」
- `2026-09-22` → `明日节气 · 秋分`；`2026-09-23` → `今日节气 · 秋分`
- `2020-06-01` → `农历 闰四月 · 初十`（闰月路径）
- 窄屏 → hero 行照常显示农历日期，侧栏挂件不做无谓计算

关于 [8]：负向验证用 1900–1906 的小窗口跑摘要（全量一次约 400ms，8 组变异会拖慢整套回归）。
窗口必须从 1900 起 —— 1899 年头 11 个月在支持范围外，会拿到 `null`（这个坑当场踩过）。

## 窄屏的处理

数据免费后，「窄屏不自动加载、点按才下载」的权衡不存在了，窄屏也直接显示农历日期。
但横向空间依旧紧张，所以：

- 生肖那截包在 `<span class="lunar-sx">` 里，`@media (max-width: 980px)` 下 `display: none`
  （保留 `丙午年八月初五`，舍掉 `（马）` —— 农历日期本身必须留下，因为窄屏右侧栏整体隐藏，
  hero 这行是唯一能看到农历的地方）
- 同一媒体查询里给 `.lunar-clock` 加 `flex-wrap: wrap`，防 320px 顶边

## 如何重新生成数据表

⚠️ **`scripts/gen-lunar-data.mjs` 需要旧库才能跑**，而旧库已被删除（它只作为参照物存在过）。
若日后要重做（换年份范围、换数据来源）：

```bash
# 1. 取回同名库（lunar-javascript 6.x，UMD 单文件）放到 assets/vendor/lunar.js
# 2. 生成内联代码块（粘进 app.js 的 LUNAR-INLINE 标记之间）
node scripts/gen-lunar-data.mjs --block /tmp/block.js
# 3. 重新生成黄金基准
node scripts/gen-lunar-data.mjs --golden scripts/fixtures/lunar-golden.json
# 4. 校验
node scripts/verify-lunar-core.mjs
```

不带参数运行会打印体积对比（年表/节气表原始与 gzip 字节数、压缩比）。

## 已知取舍

- **支持范围 1899-12-01 – 2100-12-31**（与原库一致）。超出范围 `lunarOf()` 返回 `null`，
  hero 行降级为只显示时辰（不留空、不报错）——只有系统时间被调到范围外才会触发
- **节气用表不用公式**，因为公式在 5% 的年份差一天（见上）。表的代价是 4.8KB 文本，
  gzip 后几乎不占体积
- 内联块被 `verify-lunar-core` 的 [1] 断言约束为**纯函数**：不得引用任何外部全局
  （这样它既能在浏览器里跑，也能被抽出来在 Node 里验证）
