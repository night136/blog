# 封面：阻不阻塞、为什么会不加载、怎么少下一次

起因（2026-09-15，用户配图提问）：「封面图会阻塞吗，为啥会不加载」。

## 先回答：不阻塞，但它是 LCP

用真实浏览器量（`scripts/perf-probe.mjs`，本机 Edge + CDP，不装 puppeteer）：

```
FCP 1040ms 时三张封面还在下载（1133–2072ms）
LCP 2456ms = <img class="post-cover">   ← 封面就是最大首屏内容
```

图片**从来不是渲染阻塞资源**：浏览器解析到 `<img>` 就继续渲染，不会等图。所以「封面卡住整页」
这个直觉是错的 —— 它拖的是 **LCP**（用户感觉「这页好像没画完」），不是首绘。
真正会阻塞首绘的是 `<head>` 里的跨站样式表，见 `docs/first-paint.md`。

## 「不加载」的三个真因（都不是玄学）

### ① D1 里存着**上一轮构建**的产物路径，而那个文件已经不在了

后台编辑「回存」会把快照里的构建产物路径写回 D1，而历史版本的文件名含中文 slug
（Cloudflare Pages 对非 ASCII 资源名不可靠，实测「表里登记了、文件却 404」）。
构建时原样登记就造出一条死链 → 封面永久空白。

实测案例 `2026-09-08-学会识痞-拒痞-治痞-hu59`：D1 存
`/generated/covers/2026-09-08-%E4%B8%AD%E6%96%87-slug-ab12cd34.jpg`，线上 404，
而**原图还躺在正文里**（228KB base64，md5 与 `/generated/body-images/fc7bf528.jpg` 完全一致）。

→ **自愈**：构建时若发现站内产物路径不存在，就回退到正文首图，不再直接丢掉封面。
（正文也没有图时，才允许丢成空 —— 不能瞎猜一张图出来。）

### ② 列表接口丢弃 `data:` 内联封面后直接留空

列表要防响应膨胀（实测 3 张 base64 图能让列表涨到 576KB），所以 `safeCover()` 丢掉内联封面。
但这样「静态快照有封面、API 降级路径没封面」—— 快照一失败，封面就集体消失。

→ **补映射表**：`build.mjs` 把 D1 的 `data:` 封面抽离成静态文件并输出
`generated/covers.json`（slug → 路径），列表/搜索接口查表补上。见 `functions/_lib/cover.js` 的 `listCover()`。

### ③ 分享链接打开文章时，**白下整个首页的封面**

`?post=slug` 深链下，首页整块在 300ms 后被切走，但卡片封面的 `loading="lazy"`
已经在「首页可见」的那个窗口里判定进入视口并开始下载 —— **切换视图不会取消已发出的请求**。

实测：打开一篇文章，除了它自己的封面，还偷偷下了 **5 张首页封面（643KB）**，和文章自己抢同一条跨境连接。

→ **不可见就不下载**：深链时卡片封面只写 `data-cover`（不写 `src`）、轮播只写 `data-bg`，
回到首页时由 `activateHomeCovers()` 一次性补上。见 `verify-cover-delivery.mjs` 第 [3] 节
（在 DOM 沙箱里真跑 app.js，断言渲染出的 HTML 里到底有没有 `src`）。

## 封面与正文首图共用同一个 URL（2026-09-15）

**问题**：后台用「正文首图」当封面是常态，两者是**同一份字节**，却存在两个 URL
（`/generated/covers/<slug哈希>-<内容哈希>.jpg` 与 `/generated/body-images/<内容哈希>.jpg`）。
浏览器缓存按 URL 隔离 → 同一张图下两遍。

线上实测：**7 篇有封面的文章，7 篇的封面都是正文里的图**（0 篇是独立图），封面 121–326KB。

**做法**：`build.mjs` 把正文图先落盘，再把这张清单交给 `materializeCover()`；
封面内容哈希命中清单里任意一张时，**封面直接引用那一个正文图 URL**，不再另存一份。

- 命中靠内容哈希（两者都是 sha256 前 8 位），所以正文里第 1、2、3… 张都能命中，不必是首图。
- 顺带的好处：正文首图命中的就是封面刚下好的那份缓存，从首页点进文章也不用再等一次图。

**实测效果**（真实数据真跑 build，`.diag/real-build.mjs`）：

| | 改前 | 改后 |
|---|---|---|
| 同一张图占的字节（6 篇含图文章） | 1742KB（各存两份） | **871KB** |
| `/generated/covers/` 目录 | 7 个文件 | **0 个文件** |
| 打开文章时的图片请求（单篇实测） | 6 张（同一张图下两遍，各 250KB） | **5 张（只下一次）** |
| 有封面文章的覆盖 | — | **7/7**（6 复用 + 1 自愈） |

⚠️ **随之而来的约束**：封面现在可能指向 `/generated/body-images/…`，于是
**存在性复核必须覆盖整个 `/generated/`**，不能只盯 `covers/` 子目录
（`build.mjs` 的 `ARTIFACT_PREFIX` + `functions/index.js` 的 `assetExists()` 都是通用的）。
封面文件名仍是 **纯 ASCII**（内容哈希），爬虫 `og:image` 照常可用。

## 编辑器方向的硬约束（别踩回去）

详情快照的 `body` 与 `cover` 现在都是**构建产物路径**，而编辑器从快照预填 —— 直接回存就会重演
「构建产物写回 D1、原图永久丢失」（封面事故 `3afafdd`，正文同类事故见 `docs/first-paint.md`）。

三道防线：

1. 前端「编辑」一律从 `/api/posts/detail` 取**原始**正文；取不到就**不进编辑器**（宁可重试，不能顶替）。
2. 后端 `isBuildArtifactCover()` 拒绝把 `/generated/**` 写回 `cover`（保留原值 + `coverIgnored:true`）。
3. 后端 `isBuildArtifactBody()` 对正文里的产物图片引用直接 400（响亮失败 —— 正文是用户真正在改的东西，
   静默保留会让他以为改动生效了）。判定只看图片引用，不做全文匹配：本博客写技术文章，正文里可能出现该路径的文字示例。

## 回归

- `scripts/verify-cover-delivery.mjs`（53 项）：前端不白下封面（DOM 沙箱真跑）、
  **临时目录 + mock D1 真跑 build.mjs** 验自愈与复用、列表封面取值规则、接口接线，
  外加 **2 组负向变异**（掐掉自愈分支 / 掐掉复用分支，都必须变红才能证明它们是承重的）。
- `scripts/verify-og-cover.mjs`（44 项）：爬虫 `og:image` 的取值与存在性复核，
  含「封面指向 `/generated/body-images/…`」「复用的正文图缺失」两个新场景。
- `scripts/verify-cover-persist.mjs`：构建产物路径不许写回 D1。
- `scripts/perf-probe.mjs`：真实浏览器量封面/LCP（诊断工具，非断言）。

⚠️ 写这类断言时**别把变量名写死**：本仓库出现过「把复核范围从 `covers/` 放宽到整个 `/generated/`
之后，旧断言因为找的是 `COVER_PREFIX` 而误报失败」。断言该拦的是「防御还在不在」，不是「变量是不是还叫这个名字」。

## 部署后请复测

1. 打开一篇带封面的文章（如 `2026-08-23-高敏感人怕混混痞子及奸邪小人-f4z2`），
   Network 里那张封面应**只出现一次**。
2. 用爬虫 UA 看分享卡片：
   `curl -A "facebookexternalhit/1.1" "https://blog-6p3.pages.dev/?post=<slug>" | grep og:image`
3. 后台打开「编辑」，确认正文里是原始 `data:image/...` 而不是 `/generated/body-images/…`。
